# macOS qualification report: Apple Silicon hardware pass (2026-11-24)

Paneflow was already qualified on Linux and Windows. This pass checks, on a
physical Apple Silicon Mac, that everything `docs/user/` describes works in
the real app, closes the open macOS stories in `tasks/`, and fixes what it
finds. Every verdict below names its evidence. A check that cannot be run on
this machine is marked `unavailable` with the reason, never `pass`.

Evidence files named in this report live in
[macos-20261124/](macos-20261124/): every screenshot, downscaled to
1000 px JPEG, and every command transcript, with the CLI pass under `cli/`
and the worktree pass under `worktrees/`. The full-resolution set stays
local under `tasks/evidence/macos-qualification-20261124/`, untracked.

## Decisions, open items and documentation

Every behavior `docs/user/` describes that this Mac can exercise now passes,
either as found or after a fix listed above. What remains is either a
decision that belongs to Arthur or a limit below the app.

### Decisions for Arthur

- **Self-declared `window` and `worker` principals.** A process outside every
  pane can tell the host it is the window (a `host.hello` naming
  `paneflow-desktop`, or carrying the engine identity that `paneflow host
  status` prints) or the worker (`paneflow-serve`), and can claim the window on
  the worker with `layout.attach {"client": "window"}`. It then passes the
  principal checks of `approval.follow`, `approval.decide`, `host.shutdown`
  (still refused while sessions live), `host.grants.set` and `layout.sweep`,
  and its `session.input` is accepted with the gates closed and not journaled
  (`cli/40-principals.txt`, `cli/44-session-input-journal.txt`). Pane callers
  cannot do this. `scripting.md` frames the checks as protection against a
  confused agent, not a hostile process of the same user, but it also says
  "Only the Paneflow window grants an approval". Binding these two principals
  to the caller's executable (the peer's image path, which the host can read on
  each platform) would close it; it touches `crates/paneflow-host/src/peer.rs`
  and `crates/paneflow-serve/src/server.rs`, whose identity suites run only on
  the Linux KVM matrix, so it was not changed here.
- **Accessibility of cached views.** The sidebar, terminal views and files
  sidebar leave the accessibility tree on frames that reuse their cache, the
  GPUI bug ARCHITECTURE.md already records (zed#66690) with the choice left to
  Arthur. A ready patch renders those views uncached only while an assistive
  technology is connected; measured on a debug build with an idle terminal tab,
  it rebuilds the sidebar about once per frame (52 to 56 times in 30 s) with
  app CPU within run-to-run noise (0.66 to 0.83 s against 0.31 to 0.72 s per
  30 s). Not measured on a release build or under heavy output. The patch is
  kept outside the repository, not committed.
- **Host gate refusal strings** still name `PANEFLOW_IPC_SCRIPTING`; they are
  pinned by `protocol/app-conformance-v1.json`, and `scripting.md` promises
  that a refused request keeps its former message, so this matches the docs.

### Limits below the app

- **`AXShowMenu` on a sidebar tab.** AccessKit's macOS adapter
  (`accesskit_macos` 0.26.3) exposes no show-menu action, so an assistive
  technology cannot open a tab's context menu; a right click opens it
  (`worktrees/75-tab-context-menu.jpg`). Fixing it needs AccessKit, or a
  visible menu button on each tab.
- **Settings navigation** items are not in the accessibility tree, and about
  118 click-only handlers outside settings and the palette can still miss an
  accessibility press when scrolled out of view; `on_activate` (`067287e5`)
  is the fix to apply to them. The docs promise neither.
