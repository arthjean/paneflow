== 1. An agent row stays Error after its process ended (fixed, 02bf3d2a)
Docs (features.md): the Agents section "lists the agent sessions of the active space"; "done and error stay until you type in the pane" (pane header); "A program without an agent that reports blocked or error counts toward that space button ... An error stops counting once you have looked at the pane, while the header keeps error until you type."
Before (build at main 1825a6fc): pane o-codex runs the codex stand-in, `err` -> status errored, outcome failed:Build failed, Agents row 'Codex, Codex, obs, error'.
`paneflow key o-codex ctrl-c` (not counted as typing) -> the stand-in ended, the pane is back at 'bash-3.2$'.
  40 s later: `paneflow ps --json` still lists {"pid": 7872, "tool": "codex", "state": "errored", "surface_name": "o-codex"}; worker row: foreground_runtime_id null, activity {tool codex, state errored, pid 7872}, declared_status {state error, message Build failed}.
  AX: list 'Agents' > group 'Codex, Codex, obs, error'; the tree row Tab 1 shows Error (133-item1-before-row-stays-error.png).
Cause: projected_session (src-app/src/app/host_agents.rs) drops a finished session once no agent holds the pane's foreground, but kept an errored one; the worker keeps the run while the declared error is held.
After (fixed build, same steps):
  before Ctrl+C: status errored, AX group 'Codex, Codex, obs, error' (a running errored agent is still listed)
  after Ctrl+C: `paneflow ps --json` -> {"agents": []}; AX list 'Agents' empty, the section reads 'No agents running'; the pane header keeps 'error · Build failed' (133-item1-after-row-removed.png).
Test: app::host_agents::tests::an_errored_agent_leaves_the_agents_section_once_its_process_is_gone, red before the fix ("the pane is back at its shell, so no agent session is left to list"), green after. The old assertion "a crashed agent keeps its error on screen" was removed from an_agent_that_left_the_foreground_drops_its_session_despite_its_last_hook_state.

== 2. workspace.create ignores title= (not a bug, no change)
Docs (scripting/reference.md, JSON-RPC table): `workspace.create` takes `name?`, `cwd?`, `layout?`, `space?`; the CLI verb is `new [--name]`. There is no `title` parameter, so `title=` is an unknown key and is ignored. `name` is applied, pinned by layout_pins (rig.ipc("workspace.create", {"name": "gamma"})), and used here: `paneflow new --name nb --cwd $SCRATCH/obs-fx/repo` -> {"title": "nb"}.

== 3. Cmd+W in a team lead closes the whole tab (documented, no change)
Docs (keybindings.md): close_tab = Cmd/Ctrl+W, close_pane = Cmd/Ctrl+Shift+W; features.md: "Closing the lead's pane leaves the teammates open as ordinary panes" and "Use Undo after closing a tab". Cmd+W is the tab close, so closing lead and teammates together with an Undo toast is the documented behavior.
Live check of the documented pane close: workspace nb, New tab palette (client.dispatch_action new_tab) > 'Claude Code (team)' pressed through accessibility -> lead pane 4107 'clear && CLAUDE_CODE_TMUX_TRUECOLOR=1 TMUX=paneflow-tmux-compat,0,0 TMUX_PANE=%0 PATH="~/.paneflow-dev-obs/bin/tmux-compat:$PATH" claude --teammate-mode tmux' -> stand-in ready; `split` -> SPLIT_DONE 0, teammate pane 4110 (bash) in the same tab 4105.
`paneflow focus 4107` then client.dispatch_action close_pane (Cmd+Shift+W) -> panes left: 4102 (other tab) and 4110 in tab 4105; `echo still-open-after-lead-closed` sent to 4110 ran.
