Found during the live check and fixed (659accb3): on the build of a36a5e73, an AXPress on "Close <title>" of an
unselected pane tab selected that tab instead of closing it (snapshot after the press: the tab became value=true,
both tabs still present). Cause: the close button is hidden until hover with visibility hidden, and GPUI paints no
listener for a hidden element, so it answered the press with a mouse click synthesized at the button's center, which
landed on the tab. The pane '+' was found unexposed while adding a tab (5baa76a5); on its build (window w-1890) an AXPress on button 'New tab' opened the pane New tab menu (menuitem Terminal, Claude Code, ...), and pressing menuitem Terminal added the second tab used below.

Notes on what macOS reports:
- A Tab reaches macOS as AXRadioButton (agent-desktop: radiobutton) with value true/false and the checked state; the
  tab list is AXTabGroup (tablist). Position and set size are in the node (unit tests) but agent-desktop does not print them.
- AccessKit 0.26 (accesskit_macos 0.26.3) maps neither the expanded state nor has_popup on macOS, so the Show/Hide
  wording of a fold button carries its state for VoiceOver; Windows (UIA ExpandCollapse) and Linux (AT-SPI) receive
  expanded, and UIA receives has_popup=menu for Files and Help.
- The fold button names keep the visible wording "unmodified" ("Show 31 unmodified lines"), not "unchanged", so the
  accessible name contains the visible label (WCAG 2.5.3, Label in Name).
- macOS draws the Files and Help menus in its own title bar (right of the traffic lights), so gap 3 was checked live.
