# GPUI 703b5ac3: per-paint path building (2026-11-15)

US-003 of `tasks/prd-gpui-703b5ac3-upgrade.md` measures what building and
binning paths on every paint costs on the new renderer, where `Path` is opaque
and `PaintedPath::new` bins it on each paint.

Commit: `e9adadf0f8e7` on `feat/gpui-703b5ac3`, GPUI `703b5ac3`, clean tracked
worktree. Machine: AMD Ryzen 7 7800X3D, Ubuntu 26.04 under WSL2 on Windows 11,
release profile, CPU share 1.00 on both runs. This is the CPU of the
`linux-x86_64` baseline machine (Fedora 44 on the same hardware), not its
desktop session: the timing baseline is redone on Fedora by US-019.

Command, from a clone of the commit with `CARGO_TARGET_DIR` outside the
repository (deleted afterwards):

```bash
scripts/bench-terminal.sh
```

Results: [20261115T152020Z-e9adadf0f8e7.json](20261115T152020Z-e9adadf0f8e7.json)
and [20261115T152434Z-e9adadf0f8e7.json](20261115T152434Z-e9adadf0f8e7.json).

## The three cases

Each case runs 300 timed iterations inside a real GPUI test window at scale 2,
1800 by 1000, timing only the paint closure (`terminal::perf_bench`,
`path_scenarios`).

| Metric | What one iteration paints | Run 1 p50 / p95 | Run 2 p50 / p95 | Alloc per iteration |
|---|---|---|---|---|
| `paths_tab_strip_12_badges` | 12 tab badges through `pane::paint_badge_tile`: ring, body, two-contour highlight band and rim, 48 shapes, built at their final bounds and binned | 159.2 / 188.5 us | 161.4 / 267.0 us | 394.1 KiB, 1174 allocations |
| `paths_curly_underline_200x50` | `paint_decoration_paths` over 200 by 50 cells with SGR `4:3` on every row: 50 strokes of 400 cubic segments | 10.97 / 12.32 ms | 11.22 / 12.94 ms | 21.88 MiB, 3197 allocations |
| `paths_box_drawing_200x50` | `paint_sprite_paths` over 200 by 50 cells of `╭╮╰╯╱╲╳`: one stroke per arc or diagonal, two per cross | 30.86 / 38.08 ms | 30.88 / 35.13 ms | 18.06 MiB, 202900 allocations |

The two runs agree within 2.3 % on every median.

## Squircle verdict

The 12-badge strip costs 0.16 ms per frame at the median and 0.27 ms at the
worst p95, **within the 0.4 ms budget**. US-004 therefore takes the no-cache
branch: shapes are built at their final bounds on every paint and nothing is
retained (`pane.rs`,
`a_thousand_origins_build_each_badge_where_it_paints_and_retain_nothing`).

## Terminal strokes against the previous renderer

The path cases are new, so the committed terminal baseline has no row for
them. Against the same cases run on `9f606d3aa9c1` (GPUI `37faef81`, the
commit before the upgrade, with the benchmark ported onto a dirty tree so it
could compile there:
[run 1](20261115T144517Z-9f606d3aa9c1-dirty-path-port.json),
[run 2](20261115T144536Z-9f606d3aa9c1-dirty-path-port.json)):

| Metric | `37faef81` p50 | `703b5ac3` p50 | Time | Alloc per iteration |
|---|---|---|---|---|
| `paths_tab_strip_12_badges` | 32.0 to 32.3 us | 159.2 to 161.4 us | about 5x | 891 KiB to 394 KiB |
| `paths_curly_underline_200x50` | 9.29 to 9.60 ms | 10.97 to 11.22 ms | **+14 % to +21 %** | 67.14 MiB to 21.88 MiB |
| `paths_box_drawing_200x50` | 27.37 to 28.34 ms | 30.86 to 30.88 ms | **+9 % to +13 %** | 97.02 MiB to 18.06 MiB |

The old badge figure is not comparable as such: the old renderer let Paneflow
build each badge shape once and translate it, which `703b5ac3` no longer
allows.

Two metrics sit more than 10 % above the previous renderer, both strokes:
`paths_curly_underline_200x50` (+17 % between the run means) and
`paths_box_drawing_200x50` (+11 % between the run means, +9 % to +13 %
depending on the pair of runs compared). Mitigation, carried by
US-019 or a follow-up story: rasterize each box-drawing glyph and each
undercurl cell once into GPUI's sprite atlas, as Ghostty does, so that a frame
paints sprites instead of building and binning strokes. Both cases are
full-screen worst cases; real TUIs draw arcs at frame corners and undercurl a
few diagnostics, so a normal frame pays a small fraction of them. Memory falls
3 to 5 times on the new renderer.

## The rest of the terminal suite

Against the committed `linux-x86_64/terminal.json` (`92a5c29d9902`, Fedora),
no existing metric is more than 10 % slower on both runs. The only moves above
10 % are on 10 ns-resolution metrics and do not repeat: `base_font_resolve`
+33 % then 0 % (30 ns against 40 ns), `line_text_at_220x60` +5.6 % then
-13.9 %. They are named for the US-019 re-baseline, not as regressions.

Both runs print
`layout_echo_shifted_uncached_220x60 p95 is 1.22x layout_echo_unshifted_uncached_220x60, above the 1.10x budget`.
That is a p95 ratio checked inside the suite, not a baseline comparison: the
medians of both metrics stay within 4.2 % of the baseline, and the same ratio
read 1.111 then 0.905 on two earlier runs of the new pin. It is a WSL tail
measurement for US-019 to recheck on Fedora.

## Allocation baseline

`bench/baselines/linux-x86_64/terminal-alloc.json` was refreshed with
`scripts/perf-gates.sh --refresh-alloc-baselines` on a clean clone of
`bb8621dcc886` (code identical to `e9adadf0f8e7`) to add the three path rows.
Every existing allocation column came out unchanged, and `editor-alloc.json`
was left as committed because none of its allocation values moved.

## Discarded and exploratory runs

- Two runs on a dirty tree before the US-006 badge geometry (badges 157 to
  159 us, curly 11.0 to 11.3 ms, box drawing 30.5 to 32.1 ms) informed the
  design and are not recorded.
- One run on `31d8c68ea461` was stopped before it finished: that commit was
  amended into `e9adadf0f8e7`, and a result must name a commit on the branch.
- The timings the gates profile printed during the allocation refresh are not
  recorded; only its allocation columns were used.

No pair of consecutive runs of the same case differed by more than 10 %, so
no run was discarded for spread.
