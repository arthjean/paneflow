## Timings

Against the previous timing baselines (`1090e820` for terminal, `9ecb73a6` for
editor and startup), several timings moved by 10 to 23 %. The same suites on
`3eaaafb6` show that every terminal move predates the bump: the terminal suite
reads the same on both commits within 9 %, `publish_echo_220x60` included.

In the editor suite, `open_3_7mb`, `open_markdown_injected`,
`resolve_runs_3750` and `shape_warm_60_rows` moved by 12 to 28 % in either
direction between the two single runs. None of their code changed with the
bump, and three interleaved reruns of each binary put them back within noise.

`textdiff_5k_lines_one_word_each` is faster after the bump on every run:
33.0 to 37.9 ms before, 28.0 to 28.5 ms after. Paneflow's diff code did not
change; the cause is not identified (the lockfile update moved shared crates
along with GPUI). It is an improvement, so it blocks nothing.

One editor timing got slower with the bump. `prepaint_60_rows_warm`, over three
interleaved reruns:

| Commit | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| `3eaaafb6` | 18.3 us | 18.4 us | 18.7 us |
| `92a5c29d` | 21.9 us | 22.2 us | 22.1 us |

Cause: zed#66152 removed `shape_line_by_hash`, so the bump gave the code editor
its own content-keyed `ShapeCache` (`src-app/src/app/diff_dock/code/element.rs`).
For each visible row, a warm frame now copies the rope line into a reused
buffer, hashes it, and compares the text and runs with the cached entry to
rule out a hash collision; GPUI used to trust the caller's hash. That costs
about 3.5 us per 60-row warm frame, no allocation, against a 16.7 ms frame
budget.

Startup: the median first frame is 312.7 ms (welcome), 315.2 ms (three
restored workspaces) and 312.1 ms (stale socket), 5.8 to 8.7 % below the
previous baseline. The NFR bound of 5 % above the baseline holds.

## US-008: the 30 fps cap and keystroke echo

Verdict: GO.

Rig: sway headless at 960x600 and 60 Hz, an isolated `PANEFLOW_HOME`, 200
keystrokes at 10 Hz into `cat >/dev/null`, and one workspace created every
0.25 s over IPC. The power profile was switched over D-Bus (tuned-ppd), and an
strace of the app shows it reading `ActiveProfile` as `power-saver`.

| Profile | Frames during typing (release) | Intervals of 33 ms or more | Keystrokes above 8 ms (debug probe) |
|---|---|---|---|
| `balanced` | median 17.3 ms | 34 % | 1 of 199 (83.5 ms) |
| `power-saver` | median 17.9 ms | 35 % | 0 of 199 |

The p95 from the input handler to the end of the CPU paint is 8 ms or less in
both profiles. The probe only logs values above 8 ms, so 8 ms is an upper
bound.

The cap never engaged. GPUI 37faef81 throttles a frame only when it carries a
pending next-frame callback or a forced render (`minimum_frame_interval` in
`gpui/src/window.rs`). Keystroke echo and workspace churn keep neither pending.
Paneflow's per-frame animations (hover, sidebar collapse, row motion) last
about 200 ms, and during one an echo can wait 33 ms instead of 16.7 ms, about
16 ms more.

Not measured: a sustained per-frame animation. The virtual-pointer hover hits a
38 ms floor in headless sway even in `performance`, and GNOME offers no
non-root key injection.

### US-014: what the Windows keyboard mapper does to the defaults

`KeyBinding::load` translates each chord through `WindowsKeyboardMapper` when
the binding loads, not when a key is pressed. The mapper only remaps the
digit row and the OEM keys. The table below comes from the same Win32 calls the
mapper makes (`MapVirtualKeyEx`, `ToUnicodeEx`), run for each layout on this
machine. Letter chords and named keys are outside the mapper.

| Default chord (Windows) | Action | US and UK keys | AZERTY (fr-FR) keys |
|-------------------------|--------|----------------|---------------------|
| `ctrl-1` to `ctrl-9`, `ctrl-0` | `select_workspace_N`, `font_size_reset` | Ctrl+digit | Ctrl+Shift+digit-row key (`&é"'(-è_çà`) |
| `ctrl-alt-1` to `ctrl-alt-4` | `layout_*` presets | Ctrl+Alt+digit | Ctrl+Alt+Shift+digit-row key |
| `ctrl-shift-=` | `split_equalize` | Ctrl+Shift+`=` | Ctrl+Shift+`=` |
| `ctrl-=` | `font_size_increase` | Ctrl+`=` | Ctrl+`=` |
| `ctrl--` | `font_size_decrease` | Ctrl+`-` | Ctrl+`-` (the `6` key) |
| `ctrl-,` | `open_settings` | Ctrl+`,` | Ctrl+`,` |
| `ctrl-]`, `ctrl-[` | `next_tab`, `previous_tab` | Ctrl+`]`, Ctrl+`[` | not producible |

Findings from the mapper read, each checked on hardware in the next section:

- **AZERTY `ctrl-]` and `ctrl-[`:** no unshifted or shifted key yields `[` or
  `]` (they sit on AltGr+5 and AltGr+°), so `next_tab` and `previous_tab`
  have no AZERTY chord. The mapper leaves the chord unchanged, as the
  `DummyKeyboardMapper` did before the bump, so this predates the bump.
- **AZERTY digits:** Ctrl+& does not fire `ctrl-1`, because GPUI's Windows
  input path reports the unshifted character. Ctrl+Shift+& does. The same holds
  before the bump.
- **`ctrl-shift-=`:** Windows reports Ctrl+Shift+`=` as `ctrl-+`. The
  `DummyKeyboardMapper` kept the binding as `ctrl-shift-=`, which never matched
  that input; the mapper loads it as `ctrl-+`, so the bump should fix
  `split_equalize` on Windows. Confirmed on hardware.
- **Live layout switch:** GPUI replaces `cx.keyboard_mapper()` on
  `WM_INPUTLANGCHANGE`, but bindings already loaded keep the old translation.
  Paneflow now re-applies its keybindings when the layout id changes
  (`PaneFlowApp::follow_keyboard_layout`), the same thing Zed does
  (`zed/src/zed.rs:2172`). No default chord changes translation between US and
  AZERTY. A shifted-symbol override such as `ctrl-shift-4` does: `ctrl-$` on
  US, `ctrl-4` on AZERTY.
- **Missing layout:** this machine has fr-FR AZERTY and en-GB, but no en-US
  keyboard. The hardware pass loaded en-US for the session only.

### US-015: hardware pass

**Materials.** Arthur reviewed Mica, Blurred and Acrylic on 2026-10-30 and
approved the text contrast. The approval is visual; no tool measured a ratio.

**U+2028 and U+2029.** Real ConPTY output from pwsh (`` "`u{2028}" ``) and
from Git Bash `printf` puts both separators in the grid. The surrounding text
renders and nothing panics. The DirectWrite shaping test
`the_platform_text_system_shapes_unicode_line_and_paragraph_separators`
passes.

**Detached window, quit and relaunch.** Closing a detached window with
`WM_CLOSE` leaves the app running without a panic. Quitting from the title bar
(Save, then Keep sessions running) exits with code 0 and leaves a valid
`session.json`. Two relaunches, one per build, restored the same 9
workspaces, titles and pane counts.

**WM_ENDSESSION.** With the final build running, `WM_QUERYENDSESSION` and then
`WM_ENDSESSION` (`wParam` 1, `lParam` `ENDSESSION_LOGOFF`) went to each
top-level window of the process (`Zed::Window`, `Zed::PlatformWindow` and the
IME windows). GPUI handles the message on its hidden platform window
(`gpui_windows/src/platform.rs:1244`, `handle_end_session`), and the process
exited with code 0 within 20 ms. `session.json` stayed valid and held all 10
workspaces, including one created 1.5 s before; the relaunch restored all 10.
Limitation: these were simulated messages, not a real logoff. The file
survives an abrupt exit because the save is debounced 150 ms after each change
and is written as a staged file renamed into place
(`write_session_json_inner`).

**Energy saver.** GPUI 37faef81 detects low power on Windows only through
`GUID_POWER_SAVING_STATUS` (`gpui_windows/src/platform.rs:912`). On this
desktop, which has no battery, turning on "Always use energy saver" in
Settings sets `GUID_ENERGY_SAVER_STATUS` to 1 but leaves
`GUID_POWER_SAVING_STATUS` at 0. Both values were read with
`RegisterPowerSettingNotification`. So GPUI never enters low-power mode here,
and the 30 fps cap cannot engage. Whether battery saver on a laptop sets the
legacy GUID is not verified: this machine has no battery.

Rig: the debug build with `PANEFLOW_LATENCY_PROBE=1` and a fake Claude
session held in Thinking (hook events plus an OSC 7501 `state=working`
declaration; the sidebar comet loader was drawn and animating). The scenario
types 200 keystrokes at 10 Hz into a pwsh prompt while one workspace is
created every 0.25 s over IPC. One deviation from US-008: each churn workspace
spawns a pwsh, so the oldest is closed once more than four exist, and the
create rate is unchanged. The probe logs only keystrokes above 8 ms. Every run
logged more than 10, so the nearest-rank p95, the 11th largest of 200, is
exact.

Verdict: GO. The p95 with energy saver on (27.2 to 31.1 ms) is no worse than

was measured under workspace churn in a debug build, where every create
spawns a pwsh and a ConPTY. Which part of the churn costs it was not
established, and a release build without churn was not measured.
