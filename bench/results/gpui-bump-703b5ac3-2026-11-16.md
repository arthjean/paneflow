# GPUI bump to zed@703b5ac3 (2026-11-16)

The pin moves from `37faef81` to `703b5ac3` on `feat/gpui-703b5ac3`
(`tasks/prd-gpui-703b5ac3-upgrade.md`). The commit before the bump is
`9f606d3aa` (GPUI `37faef81`); the branch head when this summary was written
is `459f2b36d`. This file gathers what the bump measured and changed. The
Linux suite runs and the timing re-baseline are done on Fedora by US-027
(PRD 1.5), which fills the section below; nothing in this file comes from a
Linux desktop session yet, apart from the US-008 check.

## Path costs (US-003)

Measured under WSL2 on the baseline CPU, not on Fedora
([paths summary](gpui-703b5ac3-paths-2026-11-15.md)), release profile, 300
iterations per case at scale 2:

| Metric | `37faef81` p50 | `703b5ac3` p50 | Time | Alloc per iteration |
|---|---|---|---|---|
| `paths_tab_strip_12_badges` | 32.0 to 32.3 us | 159.2 to 161.4 us | about 5x | 891 KiB to 394 KiB |
| `paths_curly_underline_200x50` | 9.29 to 9.60 ms | 10.97 to 11.22 ms | +14 % to +21 % | 67.14 MiB to 21.88 MiB |
| `paths_box_drawing_200x50` | 27.37 to 28.34 ms | 30.86 to 30.88 ms | +9 % to +13 % | 97.02 MiB to 18.06 MiB |

**Squircle budget: within.** The 12-badge strip costs 0.16 ms per frame at the
median and 0.27 ms at the worst p95, under the 0.4 ms budget, so no shape cache
exists: every squircle is built at its final bounds on every paint (US-004).
The old badge figure is not comparable: the old renderer let Paneflow build a
shape once and translate it, which `703b5ac3` no longer allows.

### Metrics more than 10 % above the previous renderer

| Metric | Change (run means) | Cause | Decision |
|---|---|---|---|
| `paths_curly_underline_200x50` | +17 % | GPUI `703b5ac3` turns each stroke into an outline through `tiny_skia_path` and bins it into tiles like a fill on every paint (`zed/crates/gpui/src/path_builder.rs:306-364`, #66809: "strokes are 2-8x slower"); 50 strokes of 400 cubic segments per frame | **Open, Arthur's:** accept the cost, or ship the mitigation in a follow-up story |
| `paths_box_drawing_200x50` | +11 % | the same stroke path, one stroke per arc or diagonal, two per cross, over 10,000 cells | **Open, Arthur's:** same choice |

The mitigation on the table is to rasterize each box-drawing glyph and each
undercurl cell once into GPUI's sprite atlas, as Ghostty does, so that a frame
paints sprites instead of building and binning strokes. Both cases are
full-screen worst cases; a real TUI draws arcs at frame corners and undercurls
a few diagnostics, so a normal frame pays a small fraction of them. Memory per
frame falls 3 to 5 times on the new renderer. US-027 re-measures both on Fedora.

## Frame intervals (US-009)

GPUI `703b5ac3` limits every redraw, not only forced renders and next-frame
callbacks as `37faef81` did (`zed/crates/gpui/src/window.rs:1977`, #66237).
Both Paneflow windows now state the policy instead of inheriting it
(`src-app/src/frame_policy.rs`, `paced_window_options`):

| Condition | Interval | Rate |
|---|---|---|
| Window without the keyboard focus | 33.333 ms | 30 fps, lifted during sustained high-rate input such as a scroll |
| Platform low-power mode | 33.333 ms | 30 fps |
| Serious or critical thermal pressure | 16.667 ms | 60 fps |

The longest interval that holds wins, and a mandatory platform presentation
bypasses all three. The values equal GPUI's defaults at `703b5ac3`.

**User-visible change:** an unfocused Paneflow window, such as a detached pane
on another display, updates streaming output at most 30 times per second. On
Windows it presented 68 to 70 frames per second on the old pin and 28.3 on the
new one, never more than 30 in a whole second
([frame pacing summary](gpui-703b5ac3-frame-pacing-2026-11-15.md)). Linux is
measured on Fedora by US-024.

On Windows low power is read only from `GUID_POWER_SAVING_STATUS`; Energy
Saver on this desktop sets `GUID_ENERGY_SAVER_STATUS` only, so the low-power
cap never engages here (unchanged since the `37faef81` bump).

## Keystroke latency (US-009, US-010)

Windows 11, Ryzen 7 7800X3D, RTX 4070 Ti SUPER, 2560 by 1440 at 240 Hz, debug
builds of both pins with the latency probe logging every keystroke, 200
keystrokes per run. The figure is `key-handler→paint-cpu`, from the key handler
to the end of the CPU paint of the next terminal frame; it excludes GPU
presentation and the display.

| Pin | Runs | Median (mean of run medians) | p95 (mean) |
|---|---|---|---|
| old `37faef81` | 2 | 4.99 ms | 7.10 ms |
| new `703b5ac3` | 3 | 5.57 ms | 7.67 ms |

**Within the 2 ms budget**: 0.58 ms slower at the median, less than one 240 Hz
frame (4.2 ms). Its cause was not profiled.

- **Linux:** not measured yet; US-024 runs the procedure of the frame pacing
  summary on Fedora and adds its figures here.
- **macOS: not measured.** No Mac is available before 2027, so US-010 is
  cancelled (PRD 1.2). The macOS build is validated by CI only, and the
  key-to-screen latency report of zed-industries/zed#66954 (about 18 ms more at
  120 Hz after `0373366f43`) is accepted on trust in the upstream code. The
  hardware procedure stays in the frame pacing summary.

## Rendering facts checked on hardware

- **Linux translucent windows (US-008):** translucent squircles drawn as paths
  over a translucent window blend correctly on GNOME (Mutter) and KDE Plasma
  (KWin), each on Wayland and X11, with the NVIDIA driver and with Mesa AMD
  (RADV), checked by Arthur on Fedora on 2026-11-15. The rounded-quad fallback
  is removed.
- **Windows bordered shapes (US-006):** visual pass at scale 1 on 2026-11-15;
  scale 2 is not checked, both displays of this host run at scale 1.
