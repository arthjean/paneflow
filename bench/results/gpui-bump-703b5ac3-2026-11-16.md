# GPUI bump to zed@703b5ac3 (2026-11-16)

The pin moves from `37faef81` to `703b5ac3` on `feat/gpui-703b5ac3`
(`tasks/prd-gpui-703b5ac3-upgrade.md`). The commit before the bump is
`9f606d3aa` (GPUI `37faef81`); the branch head when this summary was written
is `459f2b36d`. This file gathers what the bump measured and changed. The
Linux suites, the timing re-baseline, the Linux latency and the unfocused
frame rate were measured on Fedora by US-027 and US-024 (PRD 1.5), first on
2026-11-16 and again on 2026-11-17 and 18 once the regressions found here were
fixed; the final branch commit they measure is `650569c4`.

## Linux suites (US-027)

Machine: Arthur's Fedora 45 (the PRD says 44; the hardware is the same), AMD
Ryzen 7 7800X3D, NVIDIA GeForce RTX 4070 Ti SUPER, GNOME 51.1 on Wayland, the
hardware of every `linux-x86_64` baseline. Release profile, each commit built
in its own worktree with its own target directory outside the repository.
Every figure below comes from runs interleaved on a quiet machine (one-minute
load under 1.2 before each set, no build running, no leaked bench worker or
host): the order of the binaries is reversed every other round, every process
is pinned to CPU 2 with `taskset` (startup: CPUs 2 to 7, the app is
multithreaded), and each value is the median of the per-run medians. The CPU
share of every in-process run was 0.98 or more. Noise is measured on the same
machine in the same rounds: the final binary run again as a separate label,
and a second build of the same commit from another path. Instruction counts
come from Callgrind, one count per case, which code placement cannot move.
Every per-run value is in
[gpui-703b5ac3-us027-interleaved-2026-11-18.json](gpui-703b5ac3-us027-interleaved-2026-11-18.json).

The final commit is `650569c4`. The old pin is `9f606d3aa` (GPUI `37faef81`).
`f501e320` and `afcd1219` are the two commits around the editor regression
below. Ten rounds for the editor, twelve for the terminal, eight for startup.

**The `afcd1219` regression, fixed.** `afcd1219` (chrono replaced by jiff for
RUSTSEC-2026-0543) touches no editor code, yet opening a file got 25 to 31 %
slower than on its parent `f501e320`. The work is the same: Callgrind counts 995 653 997 against
995 652 036 instructions in `CodeDocument::new` over the suite. The hot loop is
the byte-by-byte newline split of the longest-line measure (seven instructions
a byte, `document.rs` `measure_text_lines`); its machine code is identical in
both builds, but on `f501e320` it starts at the beginning of a 64-byte line and
on `afcd1219` 48 bytes into one, straddling the next, and the 7800X3D runs it
slower. `perf annotate` puts 82 to 88 % of the cycles of `CodeDocument::new` on
the same `je` of that loop. `b42cd513` finds the newlines with memchr, which
leaves no per-byte loop for the placement to slow down: the `open_*` cases now
count 29 to 36 % fewer instructions than the old pin and time 9 to 17 % under
it.

**Two more editor costs from US-013, fixed.** Each edit re-measured its row by
folding every byte through the tab-stop width, where the old pin read the row's
character count: `keystroke_3_7mb_plain` ran 392 more instructions a keystroke
(+1.7 %) and `reload_10_hunks_100k_lines_ui` read 3 to 5 % slower. `8050f6cd`
records whether a document holds only one-column ASCII and newlines and, while
it does, takes a row's byte length: `keystroke_3_7mb_plain` now counts 4.6 %
fewer instructions than the old pin. `textdiff_300kb_50_blocks` read +4 % on
`afcd1219` and on the first memchr build with the same instructions to 0.001 %
(no code or dependency of `paneflow-textdiff` changed since the old pin); it is
back at -0.5 % without any change of its own, a placement effect.
`to_disk_string_3_7mb` reads +1.1 % in the table with the same instruction
count to 0.002 %; two later interleaved sets of the same two binaries read
the old pin 0.4 % slower (six rounds) and 1.9 % slower (twelve rounds, the
same binary again at +0.5 %), so the gap changes sign from one set to the
next and is not a cost of the code.

**`pipeline_corpus_mib_s` and `publish_echo_220x60`, fixed.** `2fc672a1` (the
SGR 58 underline color) took the conversion of a cell from 30.1 to 34.6
instructions (Callgrind, 5 886 340 cells), so the pipeline counted 2.5 % more

| `stale_socket_first_frame_total` | 301.14 ms | 301.21 ms | +0.0 % | 0.1 % | 0.7 % |

Eight rounds with `paneflow-host` built beside every app. The first startup
set of this section ran with none: `scripts/bench-startup.sh` built
`paneflow-app` alone, so a fresh target had no host and every launch took
the "no host executable" path, and the Fedora machine's `target/release`
held a host built on 2026-11-16, older than the tree the baseline was
recorded from. `e939a24c` builds the host with the app and makes the suite
refuse an app with no host beside it; the host-less set stays in the result
file as `startup_without_host` (first frame 0.3 to 1.6 % faster on the new
pin there too).

No first-frame total is slower than the old pin beyond the noise. The trace
splits each total into steps; two of them read differently on the new pin:

- `step_first_frame`, the 3.3 ms from `open_window` returning to the first
  frame request: the protocol trace (`WAYLAND_DEBUG=client`, 66 launches per
  pin) shows the app idle through it, waiting for the compositor's first
  `xdg_surface.configure`, which Mutter sends 26.1 ms after the initial
  commit for the old pin and 26.4 ms for the new one. Its sign changes with
  the scenario and the set (`restore3` -2.5 % here, +2.1 % in an earlier
  set; `welcome` from -2.9 to +3.1 % across the three builds of the new
  pin), except `stale_socket`, slower in every set (+2.3 to +5.6 %, about
  100 us). The GPUI bump alone (`988bd78f`) carries it. The GPUI change that
  reorders the first frame is zed `e20d19d32f` (#66002), which configures the
  surface once at creation instead of a 64 by 64 adapter test followed by the
  renderer's configure (`vendor/gpui_wgpu/src/wgpu_renderer.rs:509`,
  `surface_configured`). Undoing it in a measurement copy of `650569c4` brings
  `welcome_step_first_frame` back to the old pin (-0.1 %) but not
  `stale_socket` (+3.3 %), and costs 2 to 4 ms of `window_created`, so every
  total reads 0.6 to 1.1 % slower than the old pin. The `stale_socket`
  difference is not explained; it is a later compositor answer while the app
  waits, and the first frame of that scenario is not later in total;
- `restore3_step_app_state_built`, around `cx.new(PaneFlowApp::new)`: about
  220 or 300 us by run, a mode that holds for a whole set and follows the
  binary file, not the code. The same commit built from two paths reads 305
  and 231 us in one set, and the measurement copy above is the one in the
  slow mode in another. The old pin read the slow mode in 1 run of 44.

GPUI's sprite atlas through `Window::paint_svg`, as Ghostty draws its sprite
font, so a frame paints sprites instead of building and binning strokes. Both cases are
full-screen worst cases; a real TUI draws arcs at frame corners and undercurls
a few diagnostics, so a normal frame pays a small fraction of them. Memory per
frame falls 3 to 5 times on the new renderer. US-027 re-measured both on Fedora against
the old pin's path port (the "Terminal" section above).

## Frame intervals (US-009)

GPUI `703b5ac3` limits every redraw, not only forced renders and next-frame
callbacks as `37faef81` did (`zed/crates/gpui/src/window.rs:1977`, #66237).
Both Paneflow windows now state the policy instead of inheriting it
(`src-app/src/frame_policy.rs`, `paced_window_options`):

| Condition | Interval | Rate |
|---|---|---|
| Window without the keyboard focus | 33.333 ms | 30 fps, lifted during sustained high-rate input such as a scroll |
| Platform low-power mode | 33.333 ms | 30 fps |
| Serious or critical thermal pressure | 16.667 ms | 60 fps |

The longest interval that holds wins, and a mandatory platform presentation
bypasses all three. The values equal GPUI's defaults at `703b5ac3`.

**User-visible change:** an unfocused Paneflow window, such as a detached pane
on another display, updates streaming output at most 30 times per second. On
Windows it presented 68 to 70 frames per second on the old pin and 28.3 on the
new one, never more than 30 in a whole second
([frame pacing summary](gpui-703b5ac3-frame-pacing-2026-11-15.md)). On
Fedora (GNOME 51.1, Wayland, US-024) it presented 90.8 to 92.3 frames per
second on the old pin and 25.4 and 25.7 on the new one, never more than 27 in
a whole second.

On Windows low power is read only from `GUID_POWER_SAVING_STATUS`; Energy
Saver on this desktop sets `GUID_ENERGY_SAVER_STATUS` only, so the low-power
cap never engages here (unchanged since the `37faef81` bump).

## Keystroke latency (US-009, US-010)

Windows 11, Ryzen 7 7800X3D, RTX 4070 Ti SUPER, 2560 by 1440 at 240 Hz, debug
builds of both pins with the latency probe logging every keystroke, 200
keystrokes per run. The figure is `key-handler→paint-cpu`, from the key handler
to the end of the CPU paint of the next terminal frame; it excludes GPU
